# NoMoreGuessing (Access Review Tool)

A small, rule-based tool that models roles and permissions, detects two 
patterns of access risk, and requires a human to approve or reject each 
finding before it is confirmed.

> The name comes from what I saw during a real access review: without 
> documentation, who-has-what-access came down to individual memory and 
> guesswork. This tool is a small attempt to replace that guesswork with 
> a repeatable process.

## Why this exists

While reviewing administrator access for a volunteer organisation's 
management system, I mapped roughly 50 individual permissions across 
4 admin roles and found accounts still active for people whose 
volunteer status had long been inactive, along with an undocumented 
role of unclear purpose. In discussion with the senior manager, I 
learned that annual staff turnover meant no one tracked who held which 
permissions or what those permissions allowed — the knowledge relied 
on individual memory rather than documentation.

This tool is a small, self-contained attempt to turn that kind of 
manual review into something repeatable.

## What it does

1. **Models** accounts, roles, and permissions (many-to-many, via 
   junction tables)
2. **Detects** three patterns:
   - **Rule A (over-permissioned roles):** roles that hold access 
     outside the categories expected for their stated purpose
   - **Rule B (dormant accounts):** accounts still active despite no 
     login in 90+ days
   - **Rule C (risky permission combinations):** roles that combine 
     access to multiple sensitive data categories, where no single 
     permission looks dangerous on its own, but the combination does
3. **Never auto-confirms a finding.** Every detection is saved with 
   `status = pending`; a person must review and approve or reject it 
   before it counts as a confirmed risk
4. **Summarises** confirmed findings with SQL and pandas

## Why no AI in the detection logic

The rules are deterministic and hand-written, not learned from data or 
generated by a model. I wanted every decision to be explainable and 
reviewable by a person, since access-control decisions have real 
consequences and should not depend on a black box. If AI is added 
later, it would only generate a plain-language explanation of an 
already-approved finding — never make the approve/reject decision 
itself.

## Tech stack

Python, SQLAlchemy, SQLite, pandas, matplotlib

## How to run it

```bash
pip install sqlalchemy pandas matplotlib
python init_db.py      # create the schema
python seed.py         # load sample data
python rules.py        # run detection rules, save findings
python review.py       # approve/reject findings interactively
python analyze.py      # summarise confirmed findings
```

## Limitations

- **Sample data only.** The 6 accounts and 3 roles are invented, not 
  real records, so the analysis results (e.g. approval rates) have no 
  statistical meaning — they only demonstrate that the pipeline works 
  end to end
- **Thresholds are hand-picked, not validated.** The 90-day dormancy 
  window and the specific "risky" permission combination were chosen 
  by judgement, not tested against real outcomes
- **No duplicate detection.** Running `rules.py` multiple times creates 
  duplicate findings; this MVP does not yet handle re-runs
- **Rule A's "expected categories" are also hand-picked**, not derived 
  from any documented role definition — the same judgement-based 
  limitation as Rule C's risky combinations

## Possible extensions

- Rule A (over-permissioned roles)
- pytest coverage for the detection rules
- A config file for rule thresholds instead of hard-coded values
- A thin FastAPI layer for multi-reviewer approval
